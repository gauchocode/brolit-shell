# Changelog

## 3.11 - 2026-08-16

### Added

- **`migrate` task (`-t migrate -st site`, BETA)**: single-command, SSH-orchestrated migration of a Dockerized project from this server (source) to a destination server. Run only from the source. Captures via `backup_docker_project()` and triggers the destination's own `restore -st from-storage` for restore, so vhost creation, DNS updates (Cloudflare), and SSL issuance are handled by existing, tested restore logic - no new DNS/SSL code was added for this. Pre-flight checks: Docker project, SSH connectivity, Docker/Compose on the destination, brolit-shell present (bootstrap-installed if missing), Cloudflare/certbot configured on the destination, destination path collision. Optional `--decommission-source` (plus `--purge-volumes` for data deletion) stops and removes the source project, but only after the destination is verified working - both are opt-in and off by default, and the source is left completely untouched on any failure. New files: `libs/local/site_migration_helper.sh`, `utils/site_migration_manager.sh`. New menu entry: **MIGRATE SITE** (main menu 12, hidden on Proxmox nodes). v1 scope is Dockerized projects only; full design and real-world validation notes in `openspec/changes/migrate-site-between-servers/`.
- **`--transport local|dropbox` flag** for `migrate site` (default `local`): `local` rsyncs the captured backup directly to the destination via a fixed, migrate-owned staging path (`/root/.brolit_migrate_staging`, identical on both servers) - independent of `.brolit_conf.json`, so it never enables or depends on `BACKUPS.methods.local` and never affects regular/cron backups. `dropbox` instead reuses an already-configured shared Dropbox account (no rsync transfer, slower).
- **`-sm`/`--storage-method` flag** for `restore -st from-storage`: forces a specific storage method (`dropbox`/`local`/`borg`) instead of the default Dropbox > Local > Borg auto-priority. Used internally by `migrate` to tell the destination's restore which method to read from.
- **`--source-server` flag** for `restore -st from-storage`: look under a given server name's namespace in storage instead of this server's own hostname. Used internally by `migrate --transport dropbox`.
- **`--local-staging-path` flag** for `restore -st from-storage`: use this path instead of `BACKUPS.methods.local`'s configured `backup_path`, skipping the "is local storage enabled" check entirely. Used internally by `migrate --transport local`.
- **`--new-domain` / `-nd` flag** for `restore` task: allows restoring a backup to a different domain (clone). Supported with `from-storage` subtask. Usage: `runner.sh -t restore -st from-storage -D example.com -tv 2026-06-09 -nd newdomain.com`
- `subtasks_restore_handler` now accepts and passes `new_domain` to `restore_backup_from_storage_cli` (which already supported it internally).
- **Proxmox VE node support**: `proxmox_provision_openresty_vm()` (`libs/local/proxmox_helper.sh`) provisions a dedicated OpenResty gateway VM end to end from the hypervisor - creates it via `qm`, waits for SSH, installs brolit-shell + OpenResty, sets up a dedicated SSH keypair, registers a persistent NAT rule, and points the node's own config at the new VM. Reachable from the main menu as **PROXMOX TOOLS** (menu 11) whenever `proxmox_node_detect()` finds the script is running on a Proxmox VE hypervisor.
- When running on a Proxmox node, the main menu now hides the project-oriented entries (backup/restore/project/database/environment/wp-cli manager) since they operate on `PROJECTS_PATH`, which doesn't exist on the bare hypervisor.
- `certbot_helper.sh` is now Proxmox-aware end to end: `certbot_get_challenge_type()` picks DNS-01 (Cloudflare) or webroot per domain, and `certbot_certificate_install()` runs certbot on the gateway VM (via `openresty_vm_exec`) rather than locally.
- OpenResty gateway VM management now uses SSH-key-based auth exclusively (`openresty_get_ssh_key`, `openresty_vm_ssh_key_setup`) instead of password/sshpass fallback.

### Fixed

All of the following were found while implementing and end-to-end validating site migration against two real production VPS (source: `tukiverse-apps03`, destination: `epica-apps02`); all except the `migrate`-specific namespace/staging-path items are pre-existing bugs in the general backup/restore path, not introduced by `migrate`.

- `backup_docker_project()` (`libs/local/backup_helper.sh`) resolved the database container name by guessing `"${PROJECT_NAME}_mysql"`/`"${PROJECT_NAME}_postgres"` (old Compose v1 underscore convention) and the database name from the project's `.env` file. Neither holds for many real Docker Compose projects: modern Compose v2 defaults to hyphenated `<project>-<service>-1` container names (and doesn't always match a `.env`-derived `PROJECT_NAME`), and `POSTGRES_DB`/`MYSQL_DATABASE` are often set directly in `docker-compose.yml`, not `.env`. Both database backups (and hence `migrate` captures) for such projects silently used the wrong container/database name. Now resolves the container name via `docker compose config --services` + `docker compose ps` (Docker's own parser, not a fixed-indentation YAML grep), and the database name via the *running container's own environment* (`docker exec ... printenv`) - the same ground-truth approach `postgres_database_export()`/`mysql_database_export()` already used for the DB user/password.
- `storage_create_dir()` (`libs/storage_controller.sh`) ran `mkdir --force`, which is not a real `mkdir` option (GNU `mkdir` has no `--force`) - every local-storage directory creation failed with "unrecognized option". Fixed to `mkdir --parents`.
- `storage_move()` (`libs/storage_controller.sh`), used by `project_delete()` to archive old backups to an "offline" folder, had the same missing-local-path-prefix bug as `storage_upload_backup()`/`storage_download_backup()`/`storage_list_dir()` below: it passed the raw Dropbox-style relative path straight to the local `mv`, which then tried (and failed) to move a nonexistent absolute filesystem path.
- `project_delete()` (`libs/local/project_helper.sh`) checked `[[ ! -f "${PROJECTS_PATH}/${project_domain}" ]]` to verify a project exists before deleting it - but a project is a directory, not a regular file, so this check always failed with "Project directory to delete not found", even when the directory clearly existed. Affects any non-interactive call with an explicit domain (e.g. `migrate --decommission-source`).
- `_confirm_overwrite_destination()` (`libs/local/restore_backup_helper.sh`), called by restore when the destination project directory already exists, ran a blocking `whiptail --yesno` with no non-interactive bypass. Over SSH without a TTY (CLI restore, `migrate --force` retrying after a prior partial attempt), `whiptail` fails outright ("TERM environment variable needs set") instead of cleanly returning "no", leaving the restore in a partially-broken state that continued into docker build and nginx/cert steps without a properly determined project type. Now skips the prompt (and proceeds with the overwrite, matching CLI semantics) when no TTY is available.
- `project_get_port_from_env()` (`libs/local/project_helper.sh`) only checked a fixed allowlist of `.env` variable names (`WP_PORT`, `APP_PORT`, `PORT`, `SERVER_PORT`, `HTTP_PORT`, `NODE_PORT`, `WEBSERVER_PORT`). A real project using `APP_HOST_PORT` matched none of them, so Docker restore fell back to an interactive port prompt - which breaks non-interactive restore/migrate entirely. Added `APP_HOST_PORT`/`HOST_PORT` to the priority list, plus a last-resort fallback: any `*_PORT` variable not matching a known non-web-facing service (database/cache/ssh/admin), used only when exactly one candidate remains.
- `restore_project_files()` (`libs/local/restore_backup_helper.sh`) passed `--exclude=cache` to the decompress/tar step, but `backup_project_files()` (which creates the archive) does not exclude cache directories. For projects using package managers that hardlink into a cache directory (bun, npm, pnpm - `node_modules` entries hardlinked into `.bun/install/cache/`, etc.), this asymmetry meant tar could not recreate potentially thousands of hardlinks during restore ("Cannot hard link to X: No such file or directory" for every affected file), silently producing an incomplete or entirely missing project directory without a reported failure. Removed the "cache" exclude (kept `*.log`).
- `nginx_server_create()`'s "single" branch (`libs/apps/nginx_helper.sh`) declared success and created a `sites-enabled` symlink even when the template `cp` failed (e.g. because `project_type` ended up empty for any reason), leaving a dangling symlink that only surfaced later as a cryptic `nginx -t` failure during certificate installation. Now checks the `cp` result and fails closed with a clear error identifying the missing template.
- `migrate --transport dropbox` looked for the backup under this server's own `SERVER_NAME` namespace on the destination's restore, but the backup was uploaded under the *source* server's namespace in the shared Dropbox account - the destination's restore listed a path that never existed there, and `dropbox_list_directory()`'s error output for the missing path got misparsed by `awk '{print $NF}'` as if it were a real filename. Fixed via the new `--source-server` flag (see Added).
- The first working version of `migrate --transport local` required enabling `BACKUPS.methods.local` in `.brolit_conf.json` on both servers, which is also read by the regular cron backup flow - every scheduled backup on both servers would have silently started writing local copies nobody asked for. Fixed by introducing a transient `MIGRATE_LOCAL_STAGING_PATH` override (checked first, before any `BACKUPS.methods` branching) in `storage_upload_backup()`/`storage_create_dir()`/`storage_list_dir()`/`storage_download_backup()`, so `--transport local` never reads, requires, or enables that config flag at all. Also fixed a gap the refactor surfaced: `storage_download_backup()`'s Local branch was missing the `storage_method` guard entirely, so an explicit `--storage-method dropbox` call could still incorrectly also attempt a local download if `BACKUP_LOCAL_STATUS` happened to be enabled.
- Implemented the previously-scoped SSL/Cloudflare restore fix plan (`docs/plan/fix-ssl-restore-cloudflare.md`), surfaced by a spurious SSL warning during migration even though the certificate was actually issued successfully: `cloudflare_set_record()` was always forcing `proxy=false` regardless of the caller's argument (dead code overwrote it before the boolean conversion ran); the Cloudflare proxy-enable loop in `certbot_certificate_install_auto()`/`certbot_helper_installer_menu()` checked `$?` against the wrong preceding command, so it always took the "A record" branch and never the CNAME one; the DNS-propagation wait before certbot was a blind `sleep 5` with no retry, so certbot would run (and fail) even when DNS genuinely hadn't propagated yet. Added `wait_for_dns_propagation()` (`libs/commons.sh`, up to 60s retry) and now skip certbot entirely (instead of running it doomed to fail) when propagation isn't confirmed. `certbot_certificate_install_auto()`'s non-interactive Cloudflare path also now forces the Cloudflare proxy OFF before the HTTP-01 challenge step, guarding against a domain that already had it ON from a prior setup. (Two items from the original plan - the undefined `${email}` param and undefined Docker DB vars in `_configure_restored_project()` - were already fixed prior to this pass.) Known remaining gap, not part of the original plan: the proxy-enable branching treats any non-root domain as `www`-style CNAME, which is wrong for a standalone subdomain that `project_update_domain_config()` correctly creates as a plain A record - proxy re-enable then searches for a CNAME, finds none, and skips re-enabling proxy. Harmless (the site still works via the A record); flagged in the plan doc for a follow-up.
- `storage_download_backup()` (`libs/storage_controller.sh`) only had a Dropbox branch - on any server where Dropbox isn't the enabled backup method (Local-only, SFTP-only), `restore -st from-storage` reported success while downloading nothing. Added a Local branch (mirroring `storage_upload_backup()`'s existing rsync-based Local branch). SFTP/Borg download support remains a known gap (pre-existing `# TODO`).
- `storage_list_dir()` (`libs/storage_controller.sh`) checked Dropbox/Local/Borg with independent `if` blocks instead of `elif`, so when more than one method was enabled, later checks silently overwrote earlier results instead of following a defined priority. Now `elif`-chained (Dropbox > Local > Borg), matching the priority already implied elsewhere in the restore code. Also fixed the Local branch listing the wrong path (was missing the `BACKUP_LOCAL_CONFIG_BACKUP_PATH` prefix).
- `backup_project_database()` (`libs/local/backup_helper.sh`) only matched `db_engine == "psql"` for PostgreSQL, but `backup_project()`/`backup_docker_project()` pass `db_engine == "postgres"` (the convention used everywhere else in the file). A Dockerized project running PostgreSQL silently skipped its database backup on every `backup -st project`/`backup_docker_project()` run. Now accepts both `"postgres"` and `"psql"`.
- `json_read_field()` (`libs/local/json_helper.sh`) returned the literal string `"null"` for missing/absent JSON fields (a plain `jq -r` quirk), which callers' `[[ -z ]]` guards couldn't catch. Found because it silently wrote `allow null;` into a generated OpenResty config, corrupting it. Now returns an empty string via `// empty`.
- `routes.lua`'s `create_route()` symlinked `sites-enabled/<domain>` with no extension, but `nginx.conf`'s `include sites-enabled/*.conf` only matches `.conf` files - routes were written and reported success but were silently never loaded into the running config. Symlinks now carry the `.conf` suffix throughout (`create_route`, `delete_route`, `list_routes`, `get_route`).
- Certbot's ACME webroot moved from `/var/www/certbot` to `/etc/brolit/certbot-webroot` - the former broke brolit's convention that every directory under `PROJECTS.path` is a project/domain (site listing, backup, and delete code all assume this).
