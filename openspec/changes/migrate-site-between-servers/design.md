## Context

Two earlier iterations of this design were rejected during review:
1. Two independent `export`/`import` subtasks coordinated through shared remote storage — rejected because it added nothing over doing `backup`/`restore` manually.
2. A single SSH-driven command that reimplements remote bring-up itself (assuming *nothing* about the destination beyond Docker) — rejected because it would have had to reinvent DNS, SSL, and vhost handling that brolit already does, and it can't replicate DNS/backup config on a destination that isn't brolit-managed.

Investigating brolit's actual restore path resolved the tension: `restore_project_backup()` (`libs/local/restore_backup_helper.sh`) calls `_configure_restored_project()` (line 550), which calls `project_update_domain_config()` (`libs/local/project_helper.sh:3153`). That function **already**, as part of every normal restore:
- creates the nginx vhost (`nginx_server_create`)
- updates the Cloudflare DNS A/CNAME record to the current server's `${SERVER_IP}` (`cloudflare_set_record()`, when `SUPPORT_CLOUDFLARE_STATUS=enabled`)
- waits for DNS propagation and issues an SSL certificate (`certbot_certificate_install_auto()`, when `PACKAGES_CERTBOT_STATUS=enabled`)

For Docker projects, `docker_setup_configuration(mode="restore")` (line 2336) additionally handles port collisions by rewriting `.env` and picking a new port via `network_next_available_port()`. All of this is existing, tested code — a normal `restore -st from-local` run on a properly configured brolit server already does everything the user described wanting from DNS/cert automation. `migrate` therefore does not need any new DNS/SSL/vhost logic of its own; it needs to **require brolit on the destination and trigger its restore remotely**, which is a full reversal of iteration 2's "don't assume brolit on destination" decision — deliberately, because that assumption is what makes the rest of the flow so much simpler and safer (all reused, tested code paths).

## Goals / Non-Goals

**Goals:**
- One command, run only on the source server, that moves a Dockerized project to a destination server reachable by SSH, ending with the site live on the destination (vhost + DNS + SSL already handled by destination's own restore).
- Require brolit-shell on the destination, with a best-effort bootstrap-install path when it's missing, but design for the realistic v1 case where the destination is already brolit-provisioned (as `epica-apps02` is).
- Zero new DNS/SSL/vhost code — 100% reuse of the destination's own restore flow for that.
- Make source decommissioning available but strictly opt-in and strictly gated on verified destination success, since it's irreversible on a real production site.
- Never leave the source in a half-decommissioned state: decommissioning either fully completes after a verified-good migration, or isn't attempted at all.

**Non-Goals:**
- Non-Docker (host/classic) project migration and decommissioning — deferred; the underlying restore call already supports host projects, but source-side decommission semantics for host projects (which services to stop, which configs to remove) aren't defined here.
- Any new DNS or SSL logic — entirely delegated to the destination's existing restore flow.
- Persisting SSH credentials anywhere.
- Bulk/multi-project migration.
- Automatic rollback of a destination that fails mid-restore — that failure surfaces from the (reused, existing) restore command's own exit code; `migrate` does not attempt to undo a partial restore, it just reports failure and, critically, never proceeds to decommission the source in that case.
- Deleting Docker volumes (i.e. actual data) on the source by default — requires the additional explicit `--purge-volumes` flag on top of `--decommission-source`.

## Decisions

**Decision: `migrate` requires brolit-shell configured on the destination, and triggers its restore remotely via SSH instead of reimplementing DNS/SSL/vhost logic.**
This reverses the prior iteration's decision. The reversal is justified because `project_update_domain_config()` already does exactly what the user needs (vhost, DNS, cert) as a side effect of a normal restore — reimplementing it in `migrate` would mean maintaining two divergent code paths for the same outcome. The cost is that `migrate` now depends on the destination being (or becoming) a real brolit node, which is true for `epica-apps02` and is the realistic deployment model anyway (both VPS are brolit-managed).
- Alternative considered: keep reimplementing everything via raw SSH commands (prior iteration). Rejected — confirmed to duplicate large amounts of already-correct, already-tested logic (DNS record type selection for root vs www vs subdomain, HTTP/2 enablement, certbot invocation, propagation wait) for no benefit.

**Decision: pre-flight checks the destination's brolit installation and config *before* touching the source, and installs/bootstraps only as a best-effort fallback.**
`migrate_check_dest_brolit()` SSHes in and checks: `runner.sh` exists at the expected path, `.brolit_conf.json` exists, `SERVER_CONFIG` has the webserver role enabled, and (since DNS/SSL automation is expected) `SUPPORT_CLOUDFLARE_STATUS` and `PACKAGES_CERTBOT_STATUS` are both `enabled` with non-empty credentials. If brolit itself is missing, `migrate` clones the repo and generates a minimal config (webserver role only) — enough for restore to place files/containers, but explicitly **not** enough for DNS/SSL to work automatically, since Cloudflare credentials can't be safely fabricated. In that case `migrate` either fails with an actionable message, or — only if `--bootstrap-dest-config` is explicitly passed — copies the source's own `SUPPORT_CLOUDFLARE_*` config section to the destination, logging exactly what was copied.
- Alternative considered: always silently copy Cloudflare credentials to the destination if missing. Rejected — copying API credentials between servers is a real secrets-handling action that must be opt-in and visible, not a silent default.
- Note: for the real-world validation against `epica-apps02`, this whole branch (missing brolit, missing Cloudflare config) is not expected to trigger, since the destination is already provisioned — it's built for robustness/future servers and should be validated separately, not blocking the initial real-site test.

**Decision: `migrate` transfers the backup artifact directly over SSH (rsync) into the destination's own local-storage path structure, then triggers `restore -st from-storage` remotely — not `restore -st from-local`.**
Discovered during implementation: `restore -st from-local` (`restore_backup_from_local_cli()`) only restores files — no database, no vhost, no DNS, no SSL. The full automatic pipeline (files, database, port-collision handling, nginx vhost, Cloudflare DNS, certbot SSL) lives behind `restore -st from-storage` (`restore_backup_from_storage_cli()` → `restore_project_backup()` → `_configure_restored_project()`), which reads from whatever storage method (Dropbox/SFTP/Local) is configured in the *destination's own* `.brolit_conf.json`, namespaced under the destination's own `${SERVER_NAME}` (`libs/commons.sh:65`, `$HOSTNAME`). So `migrate` requires **local backup storage enabled on both source and destination** (`BACKUPS.methods.local`), and instead of transferring to an arbitrary tmp path, it rsyncs the artifact directly into `${dest_backup_local_path}/${dest_server_name}/projects-online/{site,database}/...` — the exact layout the destination would have produced had it made the backup itself. The destination's `restore -st from-storage` then finds and restores it exactly as a normal local-storage restore, no different plumbing needed on the destination side. This keeps the "no shared remote storage account" property (source and destination don't need the same Dropbox/SFTP account — each just needs *some* local storage path) while still getting the full restore pipeline for free.
Sequencing is trivial because it's all one SSH-orchestrated command: capture on source → transfer via rsync (blocks until complete) → remote restore invocation (blocks until complete, exit code captured) → verification. There's no "did the other side finish yet" coordination problem because there is no second independent process.

**Decision: source decommissioning is strictly opt-in (`--decommission-source`) and strictly gated on verified destination success.**
Given this runs against real production sites, an irreversible action (stopping the source, deleting its vhost/cert/files) must never be a side effect of testing the rest of the flow. `migrate` only reaches the decommission step if: the remote restore exited 0, AND destination verification (HTTP check) passed. Within decommissioning, actual data loss (Docker volumes) requires a second, separate flag (`--purge-volumes`) — stopping containers and removing web-facing config is comparatively recoverable (the backup artifact still exists), deleting volumes is not.
- Alternative considered: decommission automatically whenever verification passes. Rejected per explicit user decision — the operator wants to run `migrate` repeatedly against real sites without risking the source until they're confident, then opt into cleanup deliberately.

**Decision: decommissioning leaves exactly one artifact behind on the source — the backup file in brolit's tmp/backup folder.**
Order of operations: `docker compose down` (containers; volumes only with `--purge-volumes`) → remove the source's nginx vhost config and reload → remove the source's local SSL certificate files → remove the project directory → de-register the project from the source's `.brolit_conf.json`. The already-created backup artifact (used for the transfer) is deliberately left in place as the one remaining trace, matching the user's explicit request. No Cloudflare cleanup is needed on the source side — the DNS record was already repointed to the destination's IP by the destination's own restore step, not duplicated.

**Decision: transport is an explicit `--transport local|dropbox` flag, not a silent auto-detection.**
Discovered during real-server validation: `tukiverse-apps03` and `epica-apps02` both have only Dropbox enabled (`BACKUPS.methods.local` disabled on both), and share the same Dropbox app/account. Two further pre-existing bugs surfaced here: `storage_download_backup()` (`libs/storage_controller.sh`) only had a Dropbox branch (no Local branch at all — `restore -st from-storage` silently downloaded nothing on any Local-only or SFTP-only server), and `storage_list_dir()` used independent `if` blocks instead of `elif` between Dropbox/Local/Borg, so enabling more than one method made results overwrite each other unpredictably rather than following a defined priority. Both were fixed (Local branch added to `storage_download_backup()`, `elif` priority chain in `storage_list_dir()` — Dropbox > Local > Borg), since these are shared restore functions used well beyond migrate. On top of that fix, since Dropbox being enabled would otherwise always win over a newly-enabled Local method, `migrate` needed a way to force which method its own remote restore call uses — hence `--transport`, threaded through as an optional 4th parameter on `restore_backup_from_storage_cli()`/`storage_list_dir()`/`storage_download_backup()` (via a `RESTORE_STORAGE_METHOD` global for the database-download leg specifically, since `_restore_project_database()` sits deep inside `restore_project_backup()`'s call chain and threading a new parameter through every intermediate signature was judged riskier than a narrowly-scoped, clearly-commented global for this one cross-cutting concern), and exposed as a new `-sm|--storage-method` flag on `restore -st from-storage` generally (useful beyond migrate too).
`--transport local` (default) is migrate's original design: rsync the artifact directly into the destination's local-storage path structure, force `--storage-method local` on the remote restore. `--transport dropbox` skips the rsync transfer entirely (the capture step already uploaded to the shared Dropbox account, since `storage_upload_backup()` fans out to every enabled method unchanged) and forces `--storage-method dropbox` on the remote restore instead - slower (extra network hop through Dropbox) but requires no `BACKUPS.methods.local` configuration on either server, matching the environment as it's actually configured today.

**Decision (revised after real-world feedback): `--transport local` must never depend on, or implicitly require enabling, `BACKUPS.methods.local` in `.brolit_conf.json` on either server.** The first working version of `--transport local` required enabling that config flag on both servers so `backup_docker_project()`'s normal upload pipeline would produce a local copy. That's wrong: `BACKUPS.methods.local` is also read by the regular/cron backup flow (`backup_all_databases()`, `backup_all_files()`, etc.) - enabling it for migrate's benefit would make every scheduled backup on both servers start writing local copies nobody asked for, silently consuming disk. Fixed by introducing a `MIGRATE_LOCAL_STAGING_PATH` transient global override, checked first (before any config-driven branching) in the four `libs/storage_controller.sh` functions that touch local storage (`storage_upload_backup()`, `storage_create_dir()`, `storage_list_dir()`, `storage_download_backup()`): when set, each function uses that path exclusively and ignores `BACKUPS.methods.local`/`BACKUPS.methods.dropbox` entirely for that call. `migrate_capture_source()` sets it (to a fixed, migrate-owned path, `/root/.brolit_migrate_staging`, identical on both servers - not derived from any config) only for the duration of the `backup_docker_project()` call it wraps; the destination's restore receives the same path via a new `--local-staging-path` flag on `restore -st from-storage`, threaded through as a 6th parameter on `restore_backup_from_storage_cli()`. `BACKUPS.methods.local` in `.brolit_conf.json` is therefore never read, checked, or required by `--transport local` at all - the two are now fully decoupled.

## Risks / Trade-offs

- **[Risk] `migrate` triggers decommissioning based on an HTTP check that passes but the site is actually broken in some other way (e.g. correct status code, wrong content)** → Mitigation: document that `--decommission-source` is meant to be run as a deliberate second step after the operator has manually confirmed the migrated site, not necessarily glued to the same invocation that did the restore — `migrate site` can be run once without `--decommission-source` to migrate-and-verify, then re-run with `--decommission-source --force` (source already migrated, destination already exists) purely to clean up once the operator is satisfied. Document this two-phase usage pattern even though the flag makes single-invocation decommissioning possible.
- **[Risk] Copying Cloudflare credentials to a freshly bootstrapped destination (`--bootstrap-dest-config`) exposes a broader-scoped API key to a new server** → Mitigation: opt-in only, logged explicitly, documented recommendation to use a scoped Cloudflare API token rather than the global key where possible.
- **[Risk] Remote restore's DNS propagation wait (`sleep 5` fallback in `project_update_domain_config()`) is short; certbot may run before DNS has actually propagated for domains with high TTL or slow registrars** → Mitigation: not a new risk introduced by `migrate` — this is existing restore behavior; `migrate`'s own verification step catches a resulting failure and reports it before any decommissioning is considered.
- **[Risk] `--purge-volumes` deletes DB data irreversibly if used before confirming the migrated site truly has everything it needs** → Mitigation: requires two explicit flags stacked (`--decommission-source --purge-volumes`), never a default; document strongly.
- **[Trade-off] Requiring brolit on the destination makes `migrate` inapplicable to a truly bare/non-brolit server without the bootstrap path succeeding** → Accepted: matches the real deployment model (both VPS are brolit-managed) and avoids reinventing DNS/SSL/vhost logic.

## Migration Plan

1. Add new CLI flags to `libs/task_runner.sh`'s flag parser and the `case migrate)` dispatcher branch — additive only.
2. Implement `libs/local/site_migration_helper.sh`: pre-flight (Docker check, SSH connectivity, destination brolit/config check + bootstrap), capture (`backup_docker_project()`), transfer, remote restore trigger, verification, gated decommission.
3. Add `tests/test_site_migration.sh` covering pre-flight and decommission-gating logic without touching real servers.
4. Dry-run against a disposable/non-production Dockerized project on `tukiverse-apps03` → `epica-apps02`, without `--decommission-source`, first.
5. Validate CLI mode end-to-end for a real Dockerized production domain, still without `--decommission-source` initially — confirm the destination is fully correct (vhost, DNS, cert, app) before ever exercising decommission.
6. Only after a migrated site has been manually confirmed correct, exercise `--decommission-source` (without `--purge-volumes` first) against a real source, then separately validate `--purge-volumes` against a disposable project.
7. No automated rollback: since decommissioning is the last, gated, opt-in step, "rollback" of a bad migration before that point is simply "the source was never touched."

## Open Questions

- Exact destination bootstrap-install scope (`webserver` role only, or also `database`/other roles) when brolit is entirely missing — deferred, not exercised in initial real-world testing against `epica-apps02`.
- Whether `migrate` should default to a two-phase usage pattern (verify first, decommission as a separate explicit re-run) at the UX level — e.g. printing "re-run with --decommission-source to clean up the source" instead of accepting the flag on the same invocation — versus allowing both in one call as currently specified. Lean toward allowing both but documenting the two-phase pattern as the recommended approach for the first several real migrations.
- Whether host/classic project support and decommissioning should be scoped as a fast-follow once the Docker path is validated, given `project_update_domain_config()` already works for both project types — the DNS/SSL/vhost reuse argument applies equally to host projects; only decommission semantics need defining.
